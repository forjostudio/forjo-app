<objective>
**Camino de reserva pública mode-aware (CUPO-02/CUPO-05, D-12/D-13).** Tres cambios coordinados para que el modo `simultaneous_resource` funcione end-to-end en runtime, con la autoridad atómica ya en el RPC (Plan 12-01):
1. **LANDMINE — `lib/booking-core.ts`:** el re-check JS (206-218) hoy devuelve `slot_taken` cuando `taken && slotCapacity <= 1`; para un servicio simultáneo cuyo `time_block` tiene capacity 1 esto rechaza el 2º turno solapado → **el recurso nunca se llena**. El `SELECT service` (95-100) debe traer `capacity_mode`/`capacity` y el early-return volverse mode-aware.
2. **Read-path — `app/api/booking/availability`:** la rama específica se vuelve overlap-aware para servicios simultáneos (mismo solape que el RPC, `full` por solape, `busy:[]`), sin filtrar lugares restantes (D-12).
3. **Selector — `app/[slug]/booking-client.tsx`:** ocultar "Cualquiera" para simultáneos (D-13) y pasar `serviceId` en la rama específica para que el endpoint pueda calcular el solape.

Purpose: que el cliente no vea un horario que después falla en el servidor, que la 2ª camilla se pueda reservar, y que el combo no soportado "Cualquiera + simultáneo" (D-13) no se ofrezca.
Output (artifacts de este plan): `booking-core.ts` mode-aware, `availability/route.ts` overlap-aware en la rama específica, `booking-client.tsx` con el gating y el `serviceId`.
</objective>
