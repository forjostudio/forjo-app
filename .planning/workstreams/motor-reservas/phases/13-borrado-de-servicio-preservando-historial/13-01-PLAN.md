`"public"."appointments"."service_name" "text"`,

`"public"."abonos"."service_name" "text"`.

**Sección 2 — Backfill idempotente (D-04).** Dos `UPDATE … FROM services s`:
en `appointments`, setear `service_name = s.name` y `service_price = s.price` con
`WHERE s.id = a.service_id AND (a.business_id IS NULL OR s.business_id = a.business_id)

D-03). El `OR a.business_id IS NULL` evita perder filas legacy sin tenant, manteniendo el filtro
explícito para las que sí lo tienen. Comentar en español que el precio backfilleado es el **vigente
hoy**, no el histórico real (límite conocido y aceptado de D-04).

**Sección 3 — FKs a `ON DELETE SET NULL` (D-04, D-09).** Para `appointments_service_id_fkey` y para
`abonos_service_id_fkey`: `ALTER TABLE … DROP CONSTRAINT IF EXISTS …;` seguido del bloque
`DO $$ BEGIN IF NOT EXISTS (SELECT 1 FROM "pg_constraint" WHERE "conname" = … AND "conrelid" =
'"public"."<tabla>"'::"regclass") THEN ALTER TABLE … ADD CONSTRAINT … FOREIGN KEY ("service_id")
REFERENCES "public"."services"("id") ON DELETE SET NULL; END IF; END $$;`.
NO tocar `professional_services_service_id_fkey` (CASCADE) ni `professionals_service_id_fkey` (SET NULL).
Comentar que conservar el FK (en vez de dropearlo) es lo que mantiene vivo el embed `services(...)` de
PostgREST en todos los read-paths.

**Sección 4 — Función + trigger de snapshot en `appointments` (D-02, D-03).**
`CREATE OR REPLACE FUNCTION "public"."appointments_service_snapshot"() RETURNS trigger LANGUAGE plpgsql
SECURITY DEFINER SET search_path = public`, cuerpo: un único
`SELECT s.name, s.price INTO NEW.service_name, NEW.service_price FROM services s
WHERE s.id = NEW.service_id AND s.business_id = NEW.business_id;` y `RETURN NEW;`.
Reglas obligatorias a respetar y comentar en español:
- El filtro `s.business_id = NEW.business_id` es OBLIGATORIO: dentro de `SECURITY DEFINER` la RLS no
  aplica, así que un `service_id` de otro tenant NO debe resolver a nada.
- Se **sobrescribe siempre** (no "solo si viene NULL"): el snapshot no puede ser dictado por el cliente,
  o un dueño podría inflar su facturación insertando por PostgREST.
- Sin match (service_id NULL, business_id NULL o servicio de otro tenant), `SELECT … INTO` deja los
  targets en NULL: el historial cae al fallback, que es el comportamiento actual. **NO hacer RAISE.**
Luego `ALTER FUNCTION … OWNER TO "postgres";`,
`DROP TRIGGER IF EXISTS "appointments_service_snapshot_trg" ON "public"."appointments";` y
`CREATE TRIGGER "appointments_service_snapshot_trg" BEFORE INSERT ON "public"."appointments"
FOR EACH ROW EXECUTE FUNCTION "public"."appointments_service_snapshot"();`.

**Sección 5 — Función + trigger de snapshot en `abonos` (D-09).** Idéntico patrón, función
`"public"."abonos_service_snapshot"()`, copia solo `s.name` a `NEW.service_name`, mismo filtro por
`business_id`, trigger `"abonos_service_snapshot_trg" BEFORE INSERT ON "public"."abonos"`.

**Sección 6 — Función + trigger del gate de borrado (D-08, D-09, D-10).**
`CREATE OR REPLACE FUNCTION "public"."services_block_delete"() RETURNS trigger LANGUAGE plpgsql
SECURITY DEFINER SET search_path = public`, con `DECLARE v_today date :=
(now() AT TIME ZONE 'America/Argentina/Buenos_Aires')::date;`. Cuerpo, en este orden:
1. **Guard de cascada (crítico).** Si `OLD.business_id IS NOT NULL AND NOT EXISTS (SELECT 1 FROM
   businesses b WHERE b.id = OLD.business_id)` entonces `RETURN OLD` sin evaluar el gate. Motivo a
   comentar: en un `DELETE FROM businesses` la fila padre se borra ANTES de que corra la cascada a
   `services`, así que la ausencia del negocio identifica de forma confiable un borrado en cascada.
   Sin este guard, borrar la cuenta de un negocio con turnos futuros sería imposible y
   `teardownOneTenant` (test/helpers/booking-fixtures.ts) rompería toda la suite de integración.
2. `IF EXISTS (SELECT 1 FROM appointments a WHERE a.service_id = OLD.id AND (OLD.business_id IS NULL OR
   a.business_id = OLD.business_id) AND a.date >= v_today AND a.status IS DISTINCT FROM 'cancelled')
   THEN RAISE EXCEPTION 'service_has_future_appointments' USING ERRCODE = 'P0001'; END IF;`
   Comentar por qué `IS DISTINCT FROM` y no `<> 'cancelled'`: `appointments.status` es NULLABLE y el
   `<>` evalúa NULL para esas filas, dejándolas fuera del conteo y abriendo el gate.
3. `IF EXISTS (SELECT 1 FROM abonos ab WHERE ab.service_id = OLD.id AND (OLD.business_id IS NULL OR
   ab.business_id = OLD.business_id) AND ab.status = 'active') THEN RAISE EXCEPTION
   'service_has_active_abono' USING ERRCODE = 'P0001'; END IF;`
4. `RETURN OLD;` — comentar que es OBLIGATORIO: devolver NULL cancelaría el borrado **sin error** y la
   UI diría "eliminado" sin haber borrado nada.
Dos messages distintos sobre el mismo `P0001` a propósito, para que el modal pueda decir "y un abono
activo" (D-13). Luego `ALTER FUNCTION … OWNER TO "postgres";`,
`DROP TRIGGER IF EXISTS "services_block_delete_trg" ON "public"."services";` y
`CREATE TRIGGER "services_block_delete_trg" BEFORE DELETE ON "public"."services" FOR EACH ROW EXECUTE
FUNCTION "public"."services_block_delete"();`.

**Sección 7 — Cierre.** `NOTIFY pgrst, 'reload schema';`.

Todos los identificadores SQL entrecomillados como en el dump. Comentarios densos en español

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| cliente autenticado (browser, anon key + RLS) → PostgREST → `services`/`appointments`/`abonos` | El dueño puede mandar cualquier payload; el `INSERT` y el `DELETE` cruzan acá |
| función `SECURITY DEFINER` → tablas de otro tenant | Adentro de la función la RLS NO aplica; el filtro debe ser explícito |
| acción referencial `ON DELETE SET NULL` / `CASCADE` → triggers de la tabla referenciante | Postgres ejecuta la acción como un UPDATE/DELETE ordinario que dispara triggers |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-01 | Information Disclosure | `public.appointments_service_snapshot()` / `public.abonos_service_snapshot()` (SECURITY DEFINER) | mitigate | `WHERE s.id = NEW.service_id AND s.business_id = NEW.business_id` — un `service_id` de otro tenant no resuelve y el snapshot queda NULL (fail-safe) |
| T-13-02 | Tampering | INSERT en `appointments` vía PostgREST con `service_name`/`service_price` inventados (facturación inflada) | mitigate | El trigger BEFORE INSERT sobrescribe SIEMPRE las dos columnas desde `services`; nunca respeta el valor entrante |
| T-13-03 | Tampering | UPDATE del snapshot por el propio dueño vía PostgREST después del alta | accept | Son datos de su propio tenant, sin cruce entre negocios; D-03 no exige trigger de UPDATE y un BEFORE UPDATE mal escrito rompería el `service_id := NULL` de la acción referencial (docs PG). Queda registrado para secure-phase |
| T-13-04 | Elevation of Privilege | `public.services_block_delete()` (SECURITY DEFINER) contando filas de otro tenant | mitigate | Predicado sobre `a.service_id = OLD.id` (UUID PK global) + `(OLD.business_id IS NULL OR a.business_id = OLD.business_id)` — fail-closed y con filtro explícito |
| T-13-05 | Tampering | TOCTOU: se reserva un turno entre el pre-check del cliente y el DELETE, dejando turnos huérfanos en silencio | mitigate | El gate es un trigger BEFORE DELETE dentro de la misma transacción del DELETE (D-10); el `RAISE` corre antes de cualquier `SET NULL` |
