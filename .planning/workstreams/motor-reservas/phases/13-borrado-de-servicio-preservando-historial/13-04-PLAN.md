Casos:

1. **Turno futuro no cancelado bloquea (D-08, HIST-02).** Turno `status = 'confirmed'` con `date` de
   mañana → el DELETE devuelve `error` con `code === 'P0001'` y `message` que incluye
   `service_has_future_appointments`; el servicio SIGUE existiendo tras el intento.
   Este caso también confirma la asunción A2 del RESEARCH: la forma del error de un trigger
   `BEFORE DELETE` que llega por PostgREST. Registrar en el SUMMARY el objeto de error tal cual llegó.
2. **Turno futuro CANCELADO no bloquea (D-08).** Mismo turno con `status = 'cancelled'` → el DELETE
   funciona. Es la confusión original que la fase viene a arreglar.
3. **Turno futuro con `status` NULL bloquea (Pitfall 2).** Insertar el turno con `status: null` en fecha
   futura → el DELETE es rechazado con `service_has_future_appointments`. Si este test falla, el trigger
   usó `<> 'cancelled'` en vez de `IS DISTINCT FROM` y el gate está abierto.
4. **Solo turnos pasados/cancelados: borra y el historial sobrevive (HIST-01 + HIST-03).** Sembrar dos
   turnos: uno con fecha pasada `confirmed` y otro futuro `cancelled`. El DELETE funciona sin error;
   después: (a) el `select` de ese `services.id` devuelve 0 filas — prueba que `RETURN OLD` no canceló
   el borrado en silencio (T-13-06); (b) los dos turnos siguen existiendo con `service_id === null` y
   con `service_name` / `service_price` intactos.
5. **Abono `active` bloquea (D-09).** Servicio con un abono `status = 'active'` → DELETE rechazado con
   `code === 'P0001'` y `message` que incluye `service_has_active_abono`.
6. **Abono `cancelled` no bloquea y conserva el nombre (D-09).** Servicio con un abono
   `status = 'cancelled'` → DELETE OK; el abono sigue existiendo con `service_id === null` y su
   `service_name` intacto.
7. **Guard de cascada (T-13-07).** Con un servicio que TIENE un turno futuro confirmado, borrar el
   `businesses` entero: el DELETE de negocio funciona (no lo traba el gate) y el servicio desaparece.
   Este caso usa su propio tenant desechable y no llama a `teardownOneTenant` para el business (ya se
   borró), solo limpia el usuario auth.

Cada `it` con su comentario en español citando la decisión o la amenaza que cubre.
