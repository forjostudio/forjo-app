  <how-to-verify>
    **Esta acción NO la puede hacer el agente.** En este proyecto prod se aplica **a mano**, coordinado
    con el deploy: nunca por `supabase db push` ni por ningún script del flujo GSD. Las migraciones
    062/063/064 ya están en prod; la 065 es la próxima.

    Runbook (ejecutar el dueño, en este orden):
    1. Confirmar que en prod la última migración aplicada es la **064**.
    2. Abrir el SQL editor del Supabase de PRODUCCIÓN y pegar el contenido íntegro de
       `supabase/migrations/065_service_snapshot_and_delete_gate.sql`. Es idempotente: re-correrla es no-op.
    3. Verificar que el backfill corrió: los turnos históricos ya tienen `service_name` / `service_price`
       poblados (`SELECT count(*) FROM appointments WHERE service_id IS NOT NULL AND service_name IS NULL;`
       debe dar 0).
    4. Verificar que los dos FKs quedaron en SET NULL:
       `SELECT conname, confdeltype FROM pg_constraint WHERE conname IN ('appointments_service_id_fkey',
       'abonos_service_id_fkey');` → `n` en las dos filas.
    5. Ejecutar `NOTIFY pgrst, 'reload schema';` (la migración ya lo incluye al final; repetirlo si el
       editor lo separó del resto).
    6. Recién entonces desplegar el código de esta fase. El orden importa: el código nuevo lee columnas
       que solo existen después de la 065 — aunque el fallback al join lo protege, el select ampliado del
       CSV fallaría con `PGRST204` si las columnas no existen todavía.
    7. Smoke test en prod: crear un turno de prueba y verificar que su `service_name` / `service_price`
       quedaron poblados; después borrarlo.

    ⚠ El deploy y el apply van juntos. Si se despliega el código sin la 065, el CSV de Finanzas y los dos
    selects ampliados de Finanzas fallan.
  </how-to-verify>
